# KaufNest Dashboard — Code / Docs & Security Audit

**Date:** 2026-07-24
**Scope:** `kaufnest-dashboard` repository — Next.js 16 App Router app, Supabase multi-tenant (schema-per-tenant) backend, Redux Toolkit state, Stripe billing, eBay/Amazon/AliExpress integrations.
**Method:** Static review of source, SQL migrations, project docs (`README.md`, `AGENTS.md`, `SAAS_MIGRATION.md`, per-feature `CLAUDE.md`/`SKILL.md`), plus `npm audit`. No code was executed or modified.

This is a point-in-time review, not a penetration test or a guarantee of completeness. Severity ratings are the author's judgement — validate against your own threat model before acting.

---

## 1. Executive summary

The codebase is well-structured and unusually well-documented at the feature level. Most API routes enforce authentication and role checks consistently, and the multi-tenant RLS model is thoughtfully designed. The most material issues are:

- **An unauthenticated webhook (`/api/notifications/ebay-account-deletion`) that deletes tenant data** without verifying the caller is actually eBay. (High)
- **OAuth access/refresh tokens for eBay and Amazon are stored in the database in plaintext.** (High)
- **Dependency vulnerabilities** — 11 flagged by `npm audit` (7 high), including the installed Next.js version and `xlsx` (no fix available). (High)
- **Several documentation/code mismatches** that will mislead the next engineer: a referenced cron route that does not exist, `README.md` describing a single-tenant app that no longer matches reality, and migration apply-status notes that contradict each other.

Nothing here suggests active compromise; these are hardening and accuracy items.

## 2. Security findings

### 2.1 High — Unauthenticated destructive webhook (eBay account-deletion)

**File:** `src/app/api/notifications/ebay-account-deletion/route.ts`

The `POST` handler parses a JSON body, extracts `userId`/`username`, then iterates every active tenant and **deletes synced eBay sales and the eBay `platform_connections` row** for any tenant whose `external_account_id` matches.

The handler performs **no authenticity check**. The companion `GET` correctly computes the eBay challenge hash using `EBAY_VERIFICATION_TOKEN`, but the `POST` never validates the `x-ebay-signature` header (or any shared secret) before acting on the payload. Any party who can reach the public URL and who knows or guesses a tenant's eBay account id/username can trigger deletion of that tenant's synced order history and disconnect their eBay integration.

Because the work is fired async and the endpoint always returns `200`, the deletion is silent.

**Recommendation:** Verify the eBay notification signature (eBay signs these with a public key referenced by the `x-ebay-signature` header) before performing any deletion, or at minimum require a shared secret. Reject unverified requests. Consider soft-deleting rather than hard-deleting synced sales.

### 2.2 High — OAuth tokens stored in plaintext

**Files:** `src/lib/integrations/tokenStore.ts`, `supabase/migrations/008_platform_integrations.sql`, callback route.

`platform_connections.access_token` and `refresh_token` (eBay + Amazon SP-API) are written and read as plain columns. A refresh token is long-lived and grants ongoing access to a seller's marketplace account. Anyone with read access to the database (a leaked service-role key, a SQL-injection elsewhere, a backup dump, or an over-broad RLS mistake) obtains usable seller credentials.

RLS does restrict the table to admin/super_admin of the owning tenant (good), but the service-role key bypasses RLS entirely, and the tokens sit unencrypted at rest beyond whatever disk encryption Supabase provides.

**Recommendation:** Encrypt tokens at the application layer (e.g. a KMS-wrapped key, or `pgsodium`/Vault column encryption) before persisting, so a raw table read does not yield usable credentials. At minimum, document the risk and rotate on suspicion.

### 2.3 High — Dependency vulnerabilities (`npm audit`)

`npm audit` reports **11 vulnerabilities (7 high, 4 moderate)**. Notable direct dependencies:

| Package | Severity | Issue | Fix |
| --- | --- | --- | --- |
| `next` 16.2.7 (installed) | high | Multiple advisories fixed in 16.2.11 — middleware/proxy bypass, SSRF in Server Actions/rewrites, DoS, cache confusion | Upgrade to 16.2.11 (non-major) |
| `xlsx` 0.18.5 | high | Prototype pollution + ReDoS | **No fix on npm** — migrate to `xlsx` from the SheetJS CDN (`0.20.x`) or replace |
| `sharp` (transitive) | high | libvips CVEs | Pulled in via toolchain; resolved by the Next upgrade |
| `postcss`, `js-yaml`, `fast-uri`, `brace-expansion` | high/moderate | DoS / host-confusion / file-read | Mostly fixable via `npm audit fix` |
| `shadcn` / `@modelcontextprotocol/sdk` / `@hono/node-server` | moderate | Path traversal in dev tooling | Dev-time only; upgrade `shadcn` (semver-major) |

The `next` middleware/proxy-bypass advisory is especially relevant here because route protection is implemented in `src/proxy.ts` (middleware). Prioritise that upgrade.

**Recommendation:** Upgrade `next` to `16.2.11`, run `npm audit fix`, and replace or CDN-source `xlsx`. Re-run `npm audit` to confirm.

### 2.4 Medium — Impersonation issues a magic link for an arbitrary email

**File:** `src/app/api/admin/impersonate/route.ts`

The route (correctly gated to platform admins) accepts `adminEmail` from the request body and calls `service.auth.admin.generateLink({ type: "magiclink", email: adminEmail })`, returning the resulting `action_link` in the JSON response. The `adminEmail` is **not validated against the target tenant** — a platform admin can mint a login link for any email address, and the link is returned in a response body (subject to logging/proxy capture) rather than emailed.

This is admin-only, so it is not a privilege-escalation from an untrusted user, but it is broader than "impersonate this tenant's admin" and leaves a usable credential in an HTTP response.

**Recommendation:** Validate that `adminEmail` belongs to the tenant being impersonated, prefer a scoped/short-lived session mechanism over returning a raw magic link, and audit-log every impersonation.

---

### 2.5 Medium — Dropshipping table RLS is broader than the feature's intent

**Files:** `supabase/migrations/019_dropship_supplier_price.sql`, `src/app/api/dropshipping/**`

Dropshipping is intended to be **platform-admin only**, and every API route enforces `verifyPlatformAdmin`. However the table's RLS policies allow **any authenticated tenant member** to select/insert/update/delete `dropship_listings` (`USING (is_tenant_member() AND auth.role() = 'authenticated')`). The migration comment openly notes "platform-admin gating is enforced at the API layer."

So a regular tenant user who queries the table directly via the Supabase client (bypassing the Next API routes) is not blocked by RLS. Impact is limited (it is one tenant's own dropshipping data, and the UI is gated), but it is a defense-in-depth gap: the API is the only thing enforcing the platform-admin boundary.

**Recommendation:** Tighten RLS to match the intended access (e.g. gate on platform-admin membership) so the database enforces the same boundary as the API layer.

---

### 2.6 Low — Proxy fails open when the control plane is unreachable

**File:** `src/proxy.ts` (deactivated-tenant check)

The comment documents this deliberately: if the control plane is down or the tenant row is missing, `tenantRow` is null and the deactivation gate is skipped, so a deactivated tenant could continue using the app during a control-plane outage. This is an availability-vs-enforcement tradeoff, called out here for visibility rather than as a defect.

### 2.7 Low / informational — other observations

- **`.env.local` is present in the working tree with real secrets** (`SUPABASE_SERVICE_ROLE_KEY`, `CONTROL_SUPABASE_SERVICE_KEY`, `SUPABASE_ACCESS_TOKEN`, eBay secrets). It is correctly `.gitignore`d and **not tracked by git** (verified). Keep it that way; ensure it is never force-added, and rotate keys if this workspace is ever shared.
- **`SUPABASE_ACCESS_TOKEN` is a personal access token** with broad Management-API power (it edits PostgREST "exposed schemas"). Scope/rotate it carefully; its compromise affects the whole Supabase project, not just one tenant.
- **Error detail leakage:** several routes return `detail: error.message` from Postgres/Supabase to the client (e.g. provision-tenant, invite). Low risk, but it can expose schema/internal details; consider logging server-side and returning a generic message.
- **No rate limiting** is visible on auth-adjacent or scraping endpoints (login, invite, `check-prices`). Consider basic throttling, especially on anything that triggers outbound requests.
- **Fire-and-forget audit writes:** `writeAuditLog` and the invite audit insert swallow errors, so an audit entry can silently fail to record. Acceptable by design, but means the audit trail is best-effort, not guaranteed.

## 3. Documentation vs. code gaps

### 3.1 High-signal — Referenced cron route does not exist

`AGENTS.md` (lines ~44–45) documents `src/app/api/cron/sync-integrations/` as an existing "scheduled sync cron," and `.env.local.example` documents a `CRON_SECRET` "checked against the `Authorization: Bearer` header on `/api/cron/sync-integrations`." 

**Neither exists.** There is no `src/app/api/cron/` directory, no `sync-integrations` route, and no reference to `CRON_SECRET` anywhere in `src/`. `vercel.json` also defines no `crons`. So the documented scheduled order-sync is either unimplemented or was removed, while the docs and env template still advertise it. An engineer wiring up the cron in Vercel would configure a secret for an endpoint that returns 404.

**Recommendation:** Either implement the route or remove the references from `AGENTS.md`, `.env.local.example`, and add the `crons` block to `vercel.json` if/when it exists.

### 3.2 High-signal — `README.md` describes a different (single-tenant) app

`README.md` still presents KaufNest as a single-company internal tool:
- "Run the migration in the Supabase SQL editor: `supabase/migrations/001_init.sql`" — but the app is now schema-per-tenant and requires the control-plane project, `005_tenant_provisioning`, `006_bootstrap`, and many more migrations to actually run. Following the README verbatim yields a non-functional multi-tenant app.
- The Features list omits everything added since: multi-tenant SaaS, the `/admin` platform panel, Stripe billing, eBay/Amazon integrations, dropshipping, the eBay listing wizard, and the planner.
- Stack says "Supabase (Postgres + built-in Auth)" with no mention of the two-project (control plane + data plane) architecture that `SAAS_MIGRATION.md` and `AGENTS.md` describe.

**Recommendation:** Rewrite `README.md` for the current architecture, or point it at `SAAS_MIGRATION.md` / `supabase/SKILL.md` for setup and mark the quick-start as multi-tenant.

### 3.3 Medium — Migration apply-status is self-contradictory

`AGENTS.md` states migrations "004, 007, 008, control-plane 002/003" are **outstanding / pending apply**. `supabase/SKILL.md` confirms 004/007/008 are `⏳ apply now`. But `supabase/SKILL.md` also says (§ "tenant_kaufnest already exists…") that Phase 3 is verified and only "004, 007, 008" are outstanding — while simultaneously listing **many more pending migrations (010–023)** in the table above it, several marked `⏳ pending`.

The net effect: the prose summary ("outstanding: 004, 007, 008") is stale relative to the file table (which lists ~15 unapplied migrations up to `023_user_permission_overrides`). Features that depend on those migrations (order fees, pagination indexes, permission overrides, eBay listing drafts, dropshipping customs tax, the listing-images storage bucket) are code-complete but their DB changes are marked not-yet-applied. Whether the running databases actually match the code cannot be determined from the repo alone.

**Recommendation:** Reconcile the prose summary with the table, and — ideally — add a way to verify applied state (a migration ledger table) rather than tracking apply-status by hand in Markdown. Confirm on the live databases which of 004–023 are actually applied.

### 3.4 Medium — Superseded migration left in an ambiguous location

`supabase/009_dropship_listings.sql` sits **outside** the `supabase/migrations/` folder and is clearly marked "SUPERSEDED — do not apply" (replaced by `migrations/019`). Meanwhile `migrations/` jumps its own `009` slot (`009_tenant_status_rename.sql`). Two different files effectively bear the number 009 in different folders, which is a foot-gun for anyone applying migrations by globbing the tree.

**Recommendation:** Move or clearly archive the superseded file (e.g. `supabase/_archive/`) so it cannot be picked up by a "apply everything in supabase/" step.

### 3.5 Low — Middleware naming caveat is doc-only

`AGENTS.md` correctly warns that `src/proxy.ts` is this Next version's middleware equivalent and that adding `src/middleware.ts` "crashes the dev server." Verified: no `src/middleware.ts` exists. This is accurate documentation; noted only because the behaviour is unusual and load-bearing — keep the warning prominent.

### 3.6 Low — Tenant count phrasing

`AGENTS.md` says "There are 5+ live tenants"; `supabase/SKILL.md` enumerates exactly five (`tenant_kaufnest`, `tenant_waqasmumtaz`, `tenant_hochkauf`, `tenant_k2_textil`, `tenant_token`). Minor, but "5+" vs an explicit list can drift; treat the SKILL list as the source of truth or generate it.

### 3.7 Low — `REORG_PROGRESS.md` is a scratch file that outlived its purpose

`REORG_PROGRESS.md` is explicitly self-described as "Scratch file… Delete once all checkboxes are done," and its checklists are marked DONE. It remains in the repo root, adding noise.

**Recommendation:** Delete it or move it to an archive folder now that the reorg is complete.

## 4. Positive observations

- **Consistent auth guards.** API routes uniformly resolve the user via `supabase.auth.getUser()` and check role/platform-admin before acting (`requireIntegrationAdmin`, `verifyPlatformAdmin`, per-route super_admin checks). The integrations guard correctly denies accountants entirely because connections hold tokens.
- **OAuth state (CSRF) handling** in the integrations connect/callback flow uses an `httpOnly`, `secure`, `sameSite=lax`, short-lived cookie compared against the returned `state`.
- **Stripe webhook** verifies the signature with the raw body before trusting events, and the design keeps Stripe as source-of-truth for plan/status (matching the documented rule).
- **RLS design** is thorough: `is_tenant_member()` cross-tenant guard, per-role policies, and documented gotchas around PostgREST grants, exposed-schemas allowlist, and JWT refresh timing.
- **Duplicate-invite handling** in the invite/provision routes is careful about not re-stamping `app_metadata.tenant_schema` or creating duplicate profile rows.
- **Feature-level docs** (`CLAUDE.md`/`SKILL.md` per folder) are genuinely high quality and make the codebase navigable.

## 5. Prioritised remediation checklist

1. **(High)** Authenticate the eBay account-deletion webhook (verify signature) before any deletion — `ebay-account-deletion/route.ts`.
2. **(High)** Encrypt stored OAuth access/refresh tokens at the application layer — `tokenStore.ts` + migration 008.
3. **(High)** `npm audit fix`, upgrade `next` → 16.2.11, and replace/CDN-source `xlsx`; re-run `npm audit`.
4. **(Medium)** Constrain impersonation to the tenant's own admin email and stop returning raw magic links — `admin/impersonate/route.ts`.
5. **(Medium)** Tighten `dropship_listings` RLS to platform-admin so the DB matches the API boundary — migration 019.
6. **(Docs)** Fix or remove the non-existent cron references (`AGENTS.md`, `.env.local.example`, `vercel.json`).
7. **(Docs)** Rewrite `README.md` for the multi-tenant architecture.
8. **(Docs)** Reconcile migration apply-status between `AGENTS.md` prose and `supabase/SKILL.md`; verify live DB state; add a migration ledger.
9. **(Docs)** Archive superseded `supabase/009_dropship_listings.sql` and stale `REORG_PROGRESS.md`.
10. **(Low)** Add rate limiting on auth/invite/scrape endpoints; stop returning raw Postgres `error.message` to clients.
